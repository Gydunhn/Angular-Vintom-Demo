# Folder Structures for Angular Projects

Read the [original post](https://dev.to/gydunhn/optimizing-folder-structure-in-angular-projects-233k) for this documentation

## Introduction

Angular, as a framework, comes with a predefined structure. However, we can adapt it to apply the concepts of Screaming Architecture and create a folder organization that better reflects the business purpose of the application.

## Structure Levels in Angular

### Level 1: Standard Angular Structure (By type)

This is the typical structure generated by Angular CLI:

```bash
└── src/
    ├── app/
    │   ├── components/
    │   ├── services/
    │   ├── models/
    │   ├── pipes/
    │   ├── directives/
    │   └── guards/
    ├── assets/
    ├── environments/
    └── ...
```

**Advantages**:

- Familiar to Angular developers
- Follows the framework conventions

**Disadvantages**:

- Does not communicate the business purpose
- Becomes difficult to maintain as it grows
- Related modules are scattered

### Level 2: Angular Structure by Features

```bash
└── src/
    ├── app/
    │   ├── core/                 # Singleton services, global guards, etc.
    │   │   ├── services/
    │   │   ├── guards/
    │   │   └── interceptors/
    │   ├── shared/               # Shared components, pipes, directives
    │   │   ├── components/
    │   │   ├── directives/
    │   │   └── pipes/
    │   ├── features/             # Application features
    │   │   ├── auth/
    │   │   │   ├── components/
    │   │   │   ├── services/
    │   │   │   └── auth.module.ts
    │   │   ├── payment/
    │   │   │   ├── components/
    │   │   │   ├── services/
    │   │   │   └── payment.module.ts
    │   │   └── employees/
    │   │       ├── components/
    │   │       ├── services/
    │   │       └── employees.module.ts
    │   └── app.module.ts
    ├── assets/
    ├── environments/
    └── ...
```

**Advantages**:

- Organizes code by features
- Uses Angular modules to encapsulate functionalities
- Keeps shared components separated

**Disadvantages**:

- Still maintains some technical orientation instead of domain focus

### Level 3: Angular Structure with Screaming Architecture

```bash
└── src/
    ├── app/
    │   ├── core/                  # Application infrastructure
    │   │   ├── infrastructure/    # Technical implementations
    │   │   │   ├── http/
    │   │   │   ├── storage/
    │   │   │   └── auth/
    │   │   └── ui/               # Base UI components
    │   │       ├── layout/
    │   │       └── components/
    │   ├── domains/              # Business domains (modules)
    │   │   ├── hr-management/    # Domain: HR Management
    │   │   │   ├── employee-directory/  # Use case
    │   │   │   │   ├── components/
    │   │   │   │   ├── services/
    │   │   │   │   └── models/
    │   │   │   ├── payroll/      # Use case
    │   │   │   └── hr-management.module.ts
    │   │   ├── sales/            # Domain: Sales
    │   │   │   ├── product-catalog/  # Use case
    │   │   │   ├── checkout/     # Use case
    │   │   │   └── sales.module.ts
    │   │   └── customer-support/ # Domain: Customer Support
    │   │       ├── ticket-management/  # Use case
    │   │       ├── knowledge-base/     # Use case
    │   │       └── customer-support.module.ts
    │   ├── shared/               # Components shared between domains
    │   └── app.module.ts
    ├── assets/
    ├── environments/
    └── ...
```

**Advantages**:

- The structure "screams" the business purpose
- Organizes code by domains and use cases
- Makes it easier for new developers to understand the business
- Each domain can evolve independently

**Disadvantages**:

- Greater initial complexity
- Requires good domain knowledge
- May be excessive for small applications

## Practical Implementation in Angular

### 1. Using Modules for Domains

Angular has a module system that fits perfectly with the concept of domains:

```typescript
// domains/hr-management/hr-management.module.ts
@NgModule({
  declarations: [...],
  imports: [
    CommonModule,
    SharedModule,
    RouterModule.forChild([
      { path: 'employees', component: EmployeeListComponent },
      { path: 'payroll', component: PayrollComponent }
    ])
  ],
  providers: [EmployeeService, PayrollService]
})
export class HrManagementModule { }
```

### 2. State by Domain (with NGRX/NGXS)

If you use state management, each domain can have its own state:

```bash
└── domains/
    └── hr-management/
        ├── store/
        │   ├── actions/
        │   ├── reducers/
        │   ├── effects/
        │   └── selectors/
        └── ...
```

### 3. Barrel Pattern

Facilitates imports using the barrel pattern:

```typescript
// domains/hr-management/index.ts
export * from './models';
export * from './services';
export * from './components';
```

### 4. Lazy Loading

Take advantage of Angular's lazy loading to load domains only when needed:

```typescript
// In app-routing.module.ts
const routes: Routes = [
  {
    path: 'hr',
    loadChildren: () => import('./domains/hr-management/hr-management.module')
      .then(m => m.HrManagementModule)
  },
  {
    path: 'sales',
    loadChildren: () => import('./domains/sales/sales.module')
      .then(m => m.SalesModule)
  }
];
```

## Recommendations Based on Project Size

### For small projects (1-3 developers)

- Use Level 2 (by features)
- Consider using the feature folder approach without separate modules
- Maintain a `shared` folder for common elements

### For medium projects (4-10 developers)

- Use Level 2 or 3, depending on domain complexity
- Implement lazy loading for modules/domains
- Consider using NgRx/NGXS with state separated by domain

### For large projects (10+ developers)

- Fully implement Level 3 with Screaming Architecture
- Consider dividing into multiple applications or microfrontends
- Use shared libraries for common code between domains

## Transformation Example

### Before (Type-based approach)

```bash
app/
├── components/
│   ├── product-list.component.ts
│   ├── cart.component.ts
│   └── checkout-form.component.ts
├── services/
│   ├── product.service.ts
│   └── cart.service.ts
└── models/
    ├── product.model.ts
    └── cart-item.model.ts
```

### After (Screaming Architecture approach)

```bash
app/
└── domains/
    ├── catalog/
    │   ├── components/
    │   │   └── product-list.component.ts
    │   ├── services/
    │   │   └── product.service.ts
    │   └── models/
    │       └── product.model.ts
    └── shopping/
        ├── components/
        │   ├── cart.component.ts
        │   └── checkout-form.component.ts
        ├── services/
        │   └── cart.service.ts
        └── models/
            └── cart-item.model.ts
```

## Conclusion

The implementation of Screaming Architecture in Angular is perfectly viable, especially taking advantage of its module system. The key is to organize the code first by business domains, then by use cases, and finally by technical aspects.

The ideal structure will depend on the size and complexity of your project. The important thing is that, when opening the project, any developer can quickly understand what the application does, not just that it's made with Angular.
